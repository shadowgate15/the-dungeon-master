# What breaks when the game server is opened from other devices on the LAN?

Research for [#369](https://github.com/shadowgate15/the-dungeon-master/issues/369) (map [#368](https://github.com/shadowgate15/the-dungeon-master/issues/368)). It records facts and their consequences. The design decisions belong to [#370](https://github.com/shadowgate15/the-dungeon-master/issues/370), "How does the Host turn on LAN mode with dm?".

The setting: a remote Player's browser opens the Host's game server over plain HTTP at a LAN address, for example `http://192.168.1.20:4777` or `http://My-Mac.local:4777`.

Versions checked: `@sveltejs/kit` 3.1.1, `@sveltejs/adapter-node` 6.0.5, Vite 8, Node 26 (read from `node_modules` and `package.json:45-78`). Code references are to commit `c4f8910`.

## Summary

1. **Bind address.** The launcher pins `HOST=127.0.0.1` (`src/launcher/launcher.ts:85`). adapter-node reads `HOST` and `PORT` at start (default `0.0.0.0:3000`). The bind cannot change while the server runs, and `dm` reuses a running server of the same version (`launcher.ts:158-160`). So turning LAN on needs a server (re)started with a different `HOST`.
2. **Host check.** `src/hooks.server.ts:15-42` answers 403 to every browser route whose `Host` header isn't `localhost`, `127.0.0.1` or `[::1]`. A LAN IP or `.local` name gets 403 (verified below).
3. **`ORIGIN` / CSRF.** The launcher sets `ORIGIN=http://localhost:<port>` (`launcher.ts:87`). adapter-node then builds every request URL from that one origin, whatever the browser typed. SvelteKit's CSRF check refuses form actions whose `Origin` differs from it. Today that origin works for the Host. It fails for a LAN Player, and setting it to the LAN origin breaks the Host's localhost browser instead (verified below). With no `ORIGIN` at all, adapter-node assumes `https`, so form posts over plain HTTP fail for everyone.
4. **Secure context.** Plain HTTP at a LAN IP or `.local` name is **not** a secure context. The UI uses one secure-context-only API: `navigator.clipboard.writeText` in `src/lib/play/FloorComposer.svelte:62`. On a remote device it throws, because `navigator.clipboard` is undefined. Every `crypto.randomUUID()` call runs in Node on the server, where secure contexts don't apply. There are no service workers. `crypto.randomUUID()` and `crypto.subtle` would fail if browser code (for example, a Claim token) ever used them. `crypto.getRandomValues()` would work.
5. **Cookies.** The only cookie is `theme`. SvelteKit adds `Secure` unless `url.hostname === 'localhost'` over `http:`. With today's `ORIGIN` the hostname is always `localhost`, so the cookie is set without `Secure`. That works over a LAN IP too. If `ORIGIN` (or the derived URL) became a LAN address, the default would add `Secure`, and browsers drop `Secure` cookies set over `http:`.
6. **Live push.** The SSE stream (`EventSource` on `/api/events`) has no secure-context requirement and no origin logic. It works over a LAN IP once the Host check lets the request through. Plain HTTP means HTTP/1.1, so each browser allows 6 open connections per origin, and the stream holds one per tab.
7. **Firewall.** macOS Application Firewall: an unlisted app that accepts incoming connections triggers an Allow/Deny alert. Connections are denied until the user answers. With "Automatically allow downloaded signed software" on, a Developer-ID-signed `node` (the official Node.js build) is allowed without an alert. macOS 15's Local Network privacy does **not** cover listening for and accepting incoming TCP. Linux has no per-app prompt: Ubuntu's ufw is disabled by default, and Fedora Workstation's firewalld zone opens TCP 1025-65535 (so 4777) by default.
8. **Address to show.** `os.networkInterfaces()` lists the candidate addresses (`internal: false`, IPv4). There are usually several (VPN `utun*`, link-local IPv6, Docker bridges), so they need filtering. macOS publishes `<LocalHostName>.local` over Bonjour automatically.

## 1. Bind address: adapter-node, the launcher and the runtime file

### adapter-node

- The server listens on `HOST` and `PORT`, by default `0.0.0.0:3000`, or on `SOCKET_PATH`, which overrides both ([adapter-node docs, "PORT, HOST and SOCKET_PATH"](https://svelte.dev/docs/kit/adapter-node#Environment-variables-PORT-HOST-and-SOCKET_PATH)). In the installed source: `node_modules/@sveltejs/adapter-node/src/index.js:9-11` (`host = env('HOST', '0.0.0.0')`) and `:91` (`httpServer.listen({ path, host, port })`).
- Node's `listen`: with no host, Node listens on `::` when IPv6 is available, and on most OSes `::` also binds `0.0.0.0` (dual-stack) unless `ipv6Only` is set ([Node `net` docs, `server.listen()`](https://nodejs.org/api/net.html#serverlistenport-host-backlog-callback)). adapter-node always passes its `host` (default `0.0.0.0`), so in practice the choice is `0.0.0.0` (IPv4 only), `::` (dual-stack) or one specific address.
- Binding only the LAN address (for example `HOST=192.168.1.20`) would stop loopback connections. The launcher, bridge and hooks all reach the server over loopback: the launcher at `127.0.0.1` (`src/launcher/launcher.ts:40,137,203`), the bridge and hooks at `localhost` (`src/bridge/bridge.ts:75`, `src/hooks/hooks.ts:35`). So a LAN bind must still cover loopback, either with `0.0.0.0` / `::` or with more than one listener.

### The launcher (`dm`)

Source `src/launcher/launcher.ts`, bundled to `plugin/bin/dm.mjs` (`scripts/build-bridge/build.ts:9-10,38-40`). `plugin/bin/dm` is a shim that runs it.

- `startServer` spawns `plugin/server/index.js`, detached, with `PORT`, `HOST: '127.0.0.1'` and `ORIGIN: http://localhost:<port>` (`launcher.ts:69-89`). The comment at `:86` says why `ORIGIN` is set: "adapter-node assumes https otherwise, and refuses the UI's form posts as cross-site."
- The port defaults to 4777, or comes from `DUNGEON_MASTER_PORT` (`launcher.ts:16,310`; `src/lib/server/bridge/index.ts:40`).
- `ensureServer` reuses a running server when its version matches (`launcher.ts:154-165`). It restarts one only when the version differs, and before that it refuses if the Campaign has an attached DM session (`:339-341`). A server already running on loopback stays on loopback when the Host later asks for LAN. A restart also cuts every attached session's bridge stream.
- The printed URL is always `http://localhost:<port>/…` (`uiUrl`, `launcher.ts:22,333,345`).
- Arguments: only `stop` and `install-shim` are recognised (`launcher.ts:314-327`). Every other argument passes through to `claude` (`runClaude(pluginId, cwd, args)`, `:347`, `:227-233`). A new `dm` flag (for example `--lan`) must be consumed before that pass-through, or `claude` receives it.

### The runtime file

`src/lib/server/runtime.ts:9` stores `{ port, token, pid, version? }` in `<home>/runtime.json`, with mode `0600` (`:15-22`). The server writes it on start (`src/hooks.server.ts:46-49`, `src/lib/server/bridge/index.ts:43-50`). It records no bind address or LAN flag. The launcher can't tell whether a running server is LAN-exposed, and the server can't tell the UI which address to show, unless the file (or an env var) gains that.

### The bridge API on the LAN

`/api/bridge/*` skips the Host check (`src/hooks.server.ts:32`). It is gated by a bearer token (`src/lib/server/bridge/api.ts:28-32,101`), which is 24 random bytes per server start (`src/lib/server/bridge/index.ts:14`). Once the server binds beyond loopback, these routes are reachable from the LAN, still behind the token. The token never crosses the LAN: it lives in the `0600` runtime file, and every legitimate client uses loopback.

## 2. The Host check (`src/hooks.server.ts`)

- `handle` returns 403 for any request where `fromLocalhost` is false (`:7`).
- `fromLocalhost` (`:31-42`): bridge routes pass. Otherwise the raw `Host` header must parse to `localhost`, `127.0.0.1` or `[::1]` (`:15-24`). For non-GET/HEAD requests that carry `Origin`, the Origin's host must equal `Host` (`:35-41`). The check is a DNS-rebinding defence (comment `:26-30`).
- It reads the raw `Host` header, not `event.url`, so it sees what the browser typed even though `ORIGIN` rewrites `event.url`.

Verified against the committed `plugin/server` build run with `HOST=0.0.0.0 ORIGIN=http://localhost:47991`. `lsof` shows `TCP *:47991 (LISTEN)` on IPv4. `GET /campaigns` with `Host: localhost:47991` returned 200. With `Host: 192.168.50.10:47991` or `Host: mymac.local:47991` it returned **403**.

Consequence: LAN mode needs the allowed-Host set to grow (the LAN IPs, the `.local` name, or some rule). The Origin-equals-Host rule for writes already holds for a LAN page, because its Origin and Host are the same LAN host. The host-only routes (for example `POST /api/server/stop`, `src/routes/api/server/stop/+server.ts:4-11`, whose comment relies on "only a page served from this machine may call it") would then rely on whatever new rule separates the Host from remote browsers.

## 3. `ORIGIN`, `event.url` and SvelteKit's CSRF check

- adapter-node: with `ORIGIN` (or `paths.origin`) set, `public_origin` is fixed, and every request's URL is built from it (`node_modules/@sveltejs/adapter-node/src/handler.js:22-30,74-91`). Without it, the origin comes from the `Host` header, and the protocol is `PROTOCOL_HEADER`'s value **or `https`** (`handler.js:159-173`). The docs say the same: the adapter "assumes the scheme is `https`… Configure `paths.origin` or `PROTOCOL_HEADER` if that assumption is wrong, for example when serving plain HTTP directly" ([svelte.dev adapter docs, public origin](https://svelte.dev/docs/kit/adapter-node#Environment-variables-ORIGIN-PROTOCOL_HEADER-HOST_HEADER-and-PORT_HEADER)). `PROTOCOL_HEADER` / `HOST_HEADER` are meant for a trusted reverse proxy, since clients can spoof them (same page).
- SvelteKit 3 CSRF: form actions (`POST`/`PUT`/`PATCH`/`DELETE` with a form content type, or none) are refused when `Origin !== url.origin`, unless the Origin is in `csrf.trustedOrigins` (`node_modules/@sveltejs/kit/src/runtime/server/csrf.js:37-44`, `respond.js:100-133`). The check runs only in production builds, not `vite dev`. `csrf.checkOrigin` was removed in SvelteKit 3. `trustedOrigins` is build-time config, and `'*'` trusts all origins ([migrating to SvelteKit 3](https://svelte.dev/docs/kit/migrating-to-sveltekit-3), [config `csrf`](https://svelte.dev/docs/kit/configuration#csrf)). The SvelteKit 3 docs say `paths.origin` "replaces the `ORIGIN` environment variable" for adapter-node, but adapter-node 6.0.5 still reads `ORIGIN` at runtime (`handler.js:22`).
- Routes affected: the form actions in `src/routes/theme/+page.server.ts`, `src/routes/campaigns/+page.server.ts`, `src/routes/campaigns/[id]/+page.server.ts`, `.../party/+page.server.ts` and `.../begin/+page.server.ts`. The JSON `+server.ts` endpoints under `src/routes/api/` are not form content types, so SvelteKit's check skips them, and only the hooks Origin check applies.

Verified with the committed build:

| Server env                      | Request                                                          | Result                                                                                        |
| ------------------------------- | ---------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `ORIGIN=http://localhost:P`     | `POST /theme`, `Host: localhost:P`, `Origin: http://localhost:P` | 200, `Set-Cookie: theme=dark; Max-Age=31536000; Path=/; HttpOnly; SameSite=Lax` (no `Secure`) |
| `ORIGIN=http://192.168.50.10:P` | same localhost request                                           | `Cross-site POST form submissions are forbidden`                                              |
| no `ORIGIN`                     | same localhost request                                           | `Cross-site POST form submissions are forbidden` (derived origin is `https://localhost:P`)    |

Consequence: the server needs to know the correct origin for each request, over plain HTTP, for two or more hostnames at once (localhost plus one or more LAN names). One `ORIGIN` value can't do that. Facts relevant to #370: `ORIGIN` is read once at start, `trustedOrigins` is fixed at build time, and adapter-node supports a [custom server](https://svelte.dev/docs/kit/adapter-node#Custom-server) that imports `handler.js` and could set the request's protocol itself. (The installed `plugin/server` already has `handler.js` beside `index.js`.)

## 4. Secure-context-only APIs in the UI

What counts as secure: a page delivered over HTTPS, or from `127.0.0.0/8`, `::1`, `localhost` or `*.localhost`. Plain `http://` at any other host is not secure ([MDN, Secure contexts](https://developer.mozilla.org/en-US/docs/Web/Security/Secure_Contexts)). An `http://192.168.x.x` or `http://name.local` page is therefore **not** a secure context. Pages can test `window.isSecureContext`.

Sweep of browser code (`src/**/*.svelte` and non-server `src/lib/**/*.ts`) for `navigator.clipboard`, `navigator.serviceWorker`, `navigator.share`, `navigator.credentials`, `navigator.storage`, `mediaDevices`, `geolocation`, `wakeLock`, `locks`, `crypto.randomUUID`, `crypto.subtle`, `isSecureContext`, `Notification`, `PushManager`, `caches`, `showSaveFilePicker`/`showOpenFilePicker`, `BroadcastChannel`, workers, and `localStorage`/`sessionStorage`/`indexedDB`:

| Use                                                                 | Where                                                                                                                       | Secure context?                                                                                                                                                                          | Remote effect                                                                                                                                                                                                             |
| ------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `navigator.clipboard.writeText(relaunch)`                           | `src/lib/play/FloorComposer.svelte:61-65`, the "DM away" bar's Copy button (`:191-202`)                                     | Required ([MDN `writeText`](https://developer.mozilla.org/en-US/docs/Web/API/Clipboard/writeText)); `[SecureContext]` in the [Clipboard API spec](https://w3c.github.io/clipboard-apis/) | `navigator.clipboard` is undefined, so `copy()` throws a TypeError, and "Copied" never shows. Also, the bar shows the Host's absolute Campaign folder path (`:59`) and a `cd … && dm` command that only the Host can run. |
| `navigator.userAgent`                                               | `src/lib/dev/ReportIssue.svelte:59` (dev panel)                                                                             | No                                                                                                                                                                                       | None                                                                                                                                                                                                                      |
| `new EventSource('/api/events')`                                    | `src/lib/live/client.ts:10`                                                                                                 | No (the [HTML SSE section](https://html.spec.whatwg.org/multipage/server-sent-events.html) has no `[SecureContext]`)                                                                     | Works                                                                                                                                                                                                                     |
| `crypto.randomUUID()`                                               | Server only: `src/lib/server/db/schema.ts` (many), `src/lib/server/db/arc-schema.ts:20`, `src/lib/server/bridge/api.ts:136` | N/A in Node                                                                                                                                                                              | None                                                                                                                                                                                                                      |
| Service workers, `localStorage`, `crypto.subtle`, other APIs listed | none found                                                                                                                  |                                                                                                                                                                                          |                                                                                                                                                                                                                           |

Note for future work, such as a Claim the browser remembers. In the [Web Crypto IDL](https://w3c.github.io/webcrypto/#crypto-interface), `randomUUID()` and `subtle` are `[SecureContext]` but `getRandomValues()` is not ([MDN `randomUUID`](https://developer.mozilla.org/en-US/docs/Web/API/Crypto/randomUUID)). `localStorage` and cookies work in insecure contexts. Tests run on `localhost`, which is a secure context, so Playwright on `localhost` won't catch any of these failures.

## 5. Cookies

- The only cookie is `theme`, set by `src/routes/theme/+page.server.ts:20` as `{ path: '/', maxAge: ONE_YEAR, sameSite: 'lax' }`, with no explicit `secure`. It is read in `src/hooks.server.ts:8` and `src/routes/+layout.server.ts:5`.
- SvelteKit's default is `secure: !dev && !(url.hostname === 'localhost' && url.protocol === 'http:')` (`node_modules/@sveltejs/kit/src/runtime/server/cookie.js:74-79`). `url` is the adapter-built URL, so with today's `ORIGIN=http://localhost:P` every request (even a LAN one) gets a non-`Secure` cookie. That was verified above.
- Browsers: "Insecure sites (`http:`) cannot set cookies with the `Secure` attribute", except on localhost ([MDN `Set-Cookie`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie#secure)). If the request URL became the LAN origin (a LAN `ORIGIN`, or a per-request origin from item 3), the default would add `Secure`, and a remote browser would drop the cookie silently. The theme choice would then never persist. Any cookie (theme, or a future Claim cookie) needs `secure: false` set explicitly in LAN mode.
- Cookies are per host, and the port is ignored. `localhost` and `192.168.1.20` are different cookie jars, so the Host's localhost tab and a LAN tab on the same machine don't share cookies or `localStorage` (a different origin).

## 6. The live push (SSE)

- One stream, `GET /api/events` (`src/routes/api/events/+server.ts:5`, `src/lib/server/live.ts:16-49`). It sends `text/event-stream` with a 15 s keep-alive comment (`live.ts:37`) and broadcasts every message to every listener (`live.ts:19-21`), with no per-browser narrowing (the map lists that under "Not yet specified"). The client uses a relative URL (`src/lib/live/client.ts:9-10`), so it follows whatever host the page came from.
- It is a GET, so the hooks Origin check doesn't apply. Only the Host check blocks it today, and SvelteKit's CSRF check doesn't touch GET.
- Plain HTTP means HTTP/1.1 (browsers speak HTTP/2 only over TLS). "When not used over HTTP/2, SSE suffers from a limitation to the maximum number of open connections… set to a very low number (6)… per browser + domain" ([MDN `EventSource`](https://developer.mozilla.org/en-US/docs/Web/API/EventSource)). The page's other fetches share that same per-host pool. A remote Player with several tabs open on one device can exhaust it, and the Host's localhost tabs have the same limit.
- The server has no keep-alive or idle timeout setting (`IDLE_TIMEOUT` defaults to 0, `adapter-node/src/index.js:14`), so LAN streams behave like loopback ones. Wi-Fi drops are recovered by `EventSource`'s automatic reconnect, and `client.ts:12-15` invalidates all queries on reconnect.

## 7. Firewalls when listening beyond localhost

### macOS

- **Application Firewall** (System Settings > Network > Firewall). If an app not on the allowed list tries to receive a connection, macOS shows an alert "asking if you want to allow or deny the connection over the network or internet". Until the user answers, "the message remains, and any attempts to connect to the app are denied" ([Apple: Block connections to your Mac with a firewall](https://support.apple.com/guide/mac-help/block-connections-to-your-mac-with-a-firewall-mh34041/mac)). The options are "Block all incoming connections", "Automatically allow built-in software…" and "Automatically allow downloaded signed software to receive incoming connections" ([Apple: Change Firewall settings](https://support.apple.com/guide/mac-help/change-firewall-settings-on-mac-mh11783/mac); [Platform Security: Firewall](https://support.apple.com/guide/security/firewall-security-seca0e83763f/web)). None of Apple's pages says whether the firewall is on by default.
- Observed on the Host's machine: the firewall is enabled, both auto-allow options are on, and the official nvm-installed `node` is signed "Developer ID Application: Node.js Foundation (HX7739G8FX)". `socketfilterfw --getappblocked` reports "Incoming connection to …/node is permitted", so no alert appears there. **Not verified:** a `node` that isn't Developer-ID signed (Homebrew bottles are ad-hoc signed) would likely get the alert, and since rules attach to the binary, possibly again after each Node upgrade. The prompt is shown in the GUI. The server is detached with stdio going to `server.log` (`launcher.ts:72-78`), so `dm`'s terminal would say nothing about it.
- **Local Network privacy** (macOS 15+) gates _outgoing_ local traffic. "Listening for and accepting incoming TCP connections" does **not** require local network access. Command-line tools run from Terminal or over SSH, and their children, are automatically allowed anyway ([Apple TN3179, Understanding local network privacy](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy)). The game server needs no Local Network permission. A future mDNS advertisement (multicast send) would count as outgoing local traffic, but Terminal-launched tools are exempt.

### Linux

- No per-app prompt exists. Whether the port is reachable depends on the distro's firewall.
- Ubuntu: "ufw by default is initially disabled" ([Ubuntu Server docs, Firewalls](https://ubuntu.com/server/docs/how-to/security/firewalls/)). When enabled, the Host needs something like `sudo ufw allow 4777/tcp`.
- Fedora Workstation: the default `FedoraWorkstation` firewalld zone opens `tcp 1025-65535` and `udp 1025-65535` ([zone file in Fedora's firewalld package](https://src.fedoraproject.org/rpms/firewalld/raw/rawhide/f/FedoraWorkstation.xml)), so 4777 is reachable by default. Other zones and distros vary (for example `firewall-cmd --add-port=4777/tcp`).

Consequence: `dm` can't detect or answer a firewall block from the server side. A connection test from the Host itself (to its own LAN IP) goes over loopback routing and doesn't prove the firewall lets other devices in.

## 8. Which address to show the Host

- `os.networkInterfaces()` returns each interface's addresses with `address`, `netmask`, `family` (`'IPv4'`/`'IPv6'`), `mac`, `internal` (true for loopback "or similar interface that is not remotely accessible"), `scopeid` and `cidr` ([Node `os` docs](https://nodejs.org/api/os.html#osnetworkinterfaces)).
- On the Host's Mac, the non-internal list held one Wi-Fi IPv4 (`en0`), several global and ULA IPv6 addresses on `en0`, link-local `fe80::` addresses on `awdl0`/`llw0`, and six `utun*` (VPN or system tunnel) link-local IPv6 addresses. So `internal: false` alone isn't enough. A useful candidate is IPv4 (or a global IPv6) on a broadcast interface (Wi-Fi or Ethernet), skipping `utun*`, `awdl*`, `llw*`, `bridge*`, Docker's `docker0`/`br-*` and link-local `169.254/16` and `fe80::/10`. Link-local IPv6 would need a zone ID, which browsers don't accept in URLs. A machine on both Wi-Fi and Ethernet has two valid answers. A DHCP address can change while the long-lived server runs (it "runs until you stop it", README), so an address captured at start can go stale.
- mDNS on macOS: the local hostname is "your computer's name with .local added, and any spaces are replaced with hyphens", and it "identifies your Mac to Bonjour-compatible services" ([Apple: Find your computer's name and network address](https://support.apple.com/guide/mac-help/find-your-computers-name-and-network-address-mchlp1177/mac)). macOS publishes it automatically, so the server needn't advertise anything to be reachable as `Name.local`. `scutil --get LocalHostName` returns the label. On this Mac, `os.hostname()` returned `<LocalHostName>.local`, but that is the BSD hostname and can differ (for example, a manually set `HostName`). It is not a guaranteed `.local` name.
- On Linux, a `.local` name exists only if avahi-daemon (with nss-mdns) runs. **Not verified here:** whether the client devices (Windows, Android, ChromeOS) resolve `.local` reliably. Apple devices do. The IP address is the fallback that always works, assuming the Host's network allows client-to-client traffic (guest or "AP isolation" Wi-Fi networks block it).
- Both forms are insecure origins (item 4) and need adding to the Host check (item 2) and the origin handling (item 3).

## 9. Development (`pnpm dev`)

- `vite dev` listens on `localhost` by default. `--host` / `server.host: true` listens on all addresses. Vite's own host check allows `localhost`, `*.localhost` and **all IP addresses** by default, and blocks other names such as `Name.local` unless they are in `server.allowedHosts` ([Vite server options](https://vite.dev/config/server-options.html#server-allowedhosts)). `vite.config.ts` sets none of these today.
- In dev, SvelteKit skips the CSRF check (`respond.js:100`), and the cookie default isn't `Secure` (`cookie.js:78`). So dev hides problems 3 and 5. Only the hooks Host check (item 2) shows up in dev. Use the built server (`plugin/server`) to test LAN behaviour.
