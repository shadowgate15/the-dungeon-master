# implement-spec

A dev-only command that runs a spec's tickets as a deterministic loop, instead of a long-lived agent orchestrating them (ADR 0004: dev tooling may call the `claude` CLI directly).

```sh
pnpm implement-spec <spec#> [--explore]
pnpm implement-spec <spec#> --status
```

On a terminal, the run draws a live progress chart in place of console lines. The chart shows:

- a header with the spec, PR and total time
- each ticket by dependency layer, with its status glyph (`·` pending, `◐` running, `⏸` waiting out a usage limit, `●` implemented and queued, `✓` done, `✗` failed), its open blockers, its `impl`/`merge` times and attempt count (`merge (git)` and the checks' time for a ticket merged by git), its queue place, its failed check and its log (the checks log when the checks after a git merge failed, or the error that stopped its merge before any merger). Checks an earlier run left open show as queued until the live run reaches them again
- the end-of-run steps

When the frame is taller than the terminal, finished layers collapse. The final frame ends with a one-line verdict: `✓ PR #… ready`, or how many rows failed or were interrupted and how many tickets are stuck behind an open blocker or not started, `— re-run to resume`. On Ctrl-C, sessions still running show as interrupted. `NO_COLOR` turns off color. When output isn't a terminal, lines print as before.

`--status` draws one frame from `state.json` and exits. It reads the ticket graph from `gh` only when the state has none cached. While the run that wrote the state is still going (its process ID, saved with each run, is alive), clocks count up to now. Otherwise sessions it left open show as interrupted, timed to its last save, and the frame ends with the verdict.

Run it from any checkout or worktree of this repository. It resolves the main repository root from git's common directory, so the run directory and worktrees always land in the same place.

## What it does

1. Reads the spec's open sub-issues and their native GitHub `blocked_by` relationships through `gh`, once per invocation.
2. Creates the integration branch `implement-spec/<spec#>` from `main`, in its own worktree under `.claude/worktrees/`.
3. Creates the run directory and a state file listing every ticket as `pending`.
4. Prints the ready frontier: every open ticket whose blockers are all closed on GitHub or `done` in the state file.
5. Launches every ready ticket at once, with no concurrency cap. Implementers that pass the done check join a FIFO merge queue, and only one merger runs at a time. After each merge the frontier is recomputed and newly ready tickets launch straight away. The run ends when nothing is running, queued or ready.
6. Implementing a ticket: cuts its branch `implement-spec/<spec#>-<ticket#>` from the integration tip into its own worktree under `.claude/worktrees/`, records that launch commit and a fresh session ID in the state file, and runs an implementer `claude -p` session there (permission checks bypassed, on Sonnet). The session's output goes to its log, never the console.
7. Runs the done check on the implementer: it exited 0, its branch has commits beyond the launch commit, and the branch still contains the launch commit. A pass marks the ticket `implemented`; anything else marks it `failed`, keeps its worktree, and names the failed check and the log on the console. A failed ticket's dependents never launch; independent tickets carry on.
8. Merging an implemented ticket: the script first runs `git merge --no-ff <ticket branch>` itself in the integration worktree, with no inference. A clean merge is recorded as the ticket's `gitMerge` in the state file (before the checks start), then the script runs the checks there, in order, stopping at the first failure: `pnpm install --frozen-lockfile`, `pnpm lint`, `pnpm check` and `pnpm test:unit --run --project client --project server`. Their output goes to `logs/checks-<ticket#>.log`, which holds only the latest checks run, and `gitMerge` records the start and end times and the outcome (passed, or the failing step). Passing checks mark the ticket `done` with no session, then remove its worktree and publish as after a merger pass (below), printing `merged #<ticket#> by git, checks passed`. Failing checks keep the merge commit (nothing is reverted or aborted) and hand the ticket to a merger session (on Opus) with a checks-failed prompt: the merge is already committed, the failing step and the checks log path, and a request to fix the breakage and commit, not to merge. That merger's done check is the usual one, and the script doesn't re-run the checks after it; a resume of it gets the same checks-failed prompt. When git reports conflicts, or fails any other way, the script aborts the merge (if one is in progress) and hands the ticket to a merger session (on Opus) whose prompt lists the conflicting files or quotes git's error. That reason is saved with the ticket (`mergeReason`), so the merger is told it again if it is resumed or restarted. When a git call or the checks throw before any merger launched, the ticket stays `implemented` with the error saved as its `mergeError`, the run stops launching, and a re-run merges it again from the git merge, with no merger. A ticket that already has a merger session (interrupted or failed) has it resumed, with no git attempt. A ticket with no merger session whose head the integration branch already contains (a run stopped during its checks) skips the git merge and goes straight to the checks, printing `#<ticket#> is already merged, running its checks`; it then passes or fails as after a fresh clean merge.

   A merger session records a fresh session ID and runs `claude -p` in the integration worktree to merge the ticket branch. It passes when it exits 0 and the integration branch contains the ticket branch's head. A pass marks the ticket `done`, removes its worktree (the branch is kept) and pushes the integration branch to `origin`. The first pass also opens a draft PR from the integration branch into `main`, with the body `Closes #<spec#>` followed by one `Closes #<ticket#>` line per ticket, and records its number in the state file; a re-run reuses that PR. The script never closes issues itself: merging the PR does. A failure (`nonzero-exit` or `not-merged`) leaves the ticket `implemented` with its worktree, names the log, and stops new launches and merges; sessions already running finish.

9. Finishing the run, only once every ticket is `done`: a reviewer session runs `/code-review` on `main...implement-spec/<spec#>` and writes its findings to `notes/review.md`; a fixer session fixes all of them with `tdd`; a PR-writer session writes the PR description with the `pr` skill to `pr-body.md` in the run directory. All three run in the integration worktree. The script then pushes the integration branch, appends any `Closes #<spec#>` or `Closes #<ticket#>` line missing from that file, replaces the PR body from it, marks the PR ready and removes the integration worktree (the branch is kept). Each finished step (`review`, `fix`, `pr-description`, `ready`) is recorded under `steps` in the state file and skipped on a re-run. A session that exits non-zero (or a PR writer that leaves no `pr-body.md`: `no-pr-body`) fails its step, names its log and ends the run with the PR still a draft.

The run exits non-zero when any implementer, merger or end-of-run step failed. A run with a failed ticket skips the end-of-run steps, so the PR stays a draft with its minimal body and nothing else is written to GitHub. It ends by printing `failed tickets:` followed by one line per failed ticket, with the session that failed, its check and its log (or, for post-merge checks that failed before their merger launched, `checks`, the failing step and the checks log). Apart from waiting out a usage limit (below), nothing is retried within a run.

If a session stops because the account hit a Claude usage limit (its output says `You've hit your … limit · resets <time> (<zone>)`), the session isn't failed. The script prints `usage limit hit by …, waiting until …`, sleeps until a minute after the reset time, then resumes the same session with a continue prompt saying it stopped at the usage limit, and runs its done check as usual. A limit with no reset time the script can read waits an hour. Other sessions keep running while one waits.

If a `git` or `gh` call around an implementer or merger throws (adding a worktree, reading a head, the done check), only that session fails, with the check `error` and the error's message on the console and in its outcome. An implementer error fails its ticket and independent tickets carry on; a merger error counts as a failed merger.

A run in which nothing failed but some open ticket never became `done` (a blocker outside the spec is still open) also exits non-zero and skips the end-of-run steps. It prints `stuck tickets:` followed by one line per stuck ticket with its open blockers. Tickets closed on GitHub since an earlier run aren't read, so they never count as stuck. A spec with no open tickets exits non-zero straight away, printing `spec #<spec#> has no open tickets`, without cutting a branch or running a session.

With `--explore`, one explorer `claude -p` session runs in the integration worktree before any implementer and writes Markdown notes to the run's `notes/` directory, which every later prompt points at. Its session and status are recorded under `steps.explore` in the state file; once it is `done`, re-runs skip it. A failed explorer (non-zero exit) ends the run before any implementer launches. Without the flag no explorer runs.

## The run directory

`.implement-spec/<spec#>/` at the main repository root, gitignored:

| Path         | Contents                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `state.json` | The integration branch and worktree, each ticket's status, launch commit, implementer and merger sessions (ID and outcome), its git merge (`gitMerge`: times and checks outcome), why that merge went to a merger (`mergeReason`) or the error that stopped it before any merger (`mergeError`) and place in the merge queue (`finishOrder`), each step not tied to a ticket (`steps.explore`, `review`, `fix`, `pr-description`, `ready`), the PR number (`pr`) and whether it was marked ready (`prReady`). Sessions also record `startedAt`/`endedAt`, `activeMs`, `attempts` and `waitingUntil`; `graph` caches the tickets and `runs` each run's span and process ID, for the chart. |
| `run.log`    | Every console line with its ISO time, under a `--- run started` header per run (`, resume of N sessions` when it resumes any). Each resume names its reason.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| `notes/`     | Shared notes for the run's sessions, including the explorer's.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| `pr-body.md` | The PR description the PR writer wrote, with any missing `Closes` lines appended.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `logs/`      | One log per session: `<role>-<ticket#>.log`, or `<role>.log` for a role not tied to a ticket (`explorer.log`, `reviewer.log`, `fixer.log`, `pr-writer.log`); and `checks-<ticket#>.log`, the latest checks after a ticket's clean git merge.                                                                                                                                                                                                                                                                                                                                                                                                                                              |

## Re-running

Running the command again for the same spec reuses the integration branch, its worktree, the state file and the PR. Tickets already in the state keep their status; tickets added to the spec since the last run are added as `pending`.

Every `claude` session runs on its role's model, passed as `--model <alias>` on every launch, fresh or resumed: the explorer, implementers and the PR writer on `sonnet`, mergers, the reviewer and the fixer on `opus` (`ROLE_MODELS` in `run-spec.ts`; there is no override). Every `claude` session starts with a fresh script-generated `--session-id`, written to the state file before it launches, and never with `--no-session-persistence`. A re-run resumes every session that didn't complete, instead of starting it fresh: one left running when the previous run stopped, or one that ended failed. It runs `claude -p --resume <id>` in the session's original directory (the ticket worktree for an implementer, the integration worktree for the explorer, mergers and end-of-run roles) and logs to the same file, with a short continue prompt: the previous session didn't complete, the reason the script recorded (interrupted, the exit code, the failed done check, or the error), then the original prompt with its pointers. When it exits, the same done check runs again. Each resume prints `resumed … because <reason>` in place of `launched …`. A session the stopped run left mid-attempt, or waiting out a usage limit, is counted as having ended at that run's last save, so its time so far is kept. If `claude` has no saved conversation for the ID (the run stopped before `claude` saved it, so `--resume` prints `No conversation found`), the script starts a fresh session in the same directory with a new ID, saved before it launches, and the same continue prompt, printing `no saved session to resume for …, launched fresh`.

In order, a re-run:

1. Resumes the explorer, with `--explore`, if it didn't complete.
2. Resumes each merger that didn't complete, one at a time, before anything else launches. If one fails again, the run stops there.
3. Queues tickets left `implemented` with no merger for merging, in the order their implementers finished.
4. Resumes implementers that didn't complete, their tickets going back to `running`, alongside launching the ready frontier. A resumed ticket's dependents launch once it merges.
5. Resumes the first end-of-run step that didn't complete; finished steps are skipped.

A re-run after the PR was marked ready (`steps.ready` is `done`) does nothing: it prints that the spec is finished and exits 0, without reading GitHub or recreating the integration worktree. A re-run after the `ready` step stopped part-way repeats it safely: once the PR is marked ready (`prReady`), it is not marked again.

To start over, delete `.implement-spec/<spec#>/`, the integration worktree and the `implement-spec/<spec#>` branch.

## Code

- `main.ts`: parses arguments, builds the real ports and calls `runSpec`.
- `run-spec.ts`: `runSpec(spec, options, ports)`, the whole run behind the tracker, git, claude and checks ports.
- `prompts.ts`: each role's prompt, pointers plus the role's instructions.
- `chart.ts`: `render(state, tickets, options)`, the progress chart as text, pure.
- `ports.ts`: the real ports, thin wrappers over `gh`, `git`, `claude` and `pnpm` (the checks).
- `usage-limit.ts`: reads a usage-limit message and the time it resets.
- `run-spec.spec.ts`: whole runs against fake ports and a temp repository root.
